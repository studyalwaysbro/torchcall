Synthesis

deepseek

## Verdict Hypothesis **A** is correct — the 3-arg `filters` table is the trigger, and the 2-arg text form is the callable path — with one important correction to the self-heal design. **The adversarial objection is right on the pivotal point and it changes the fix.** I verified it against the actual code and the fuzz mock. --- ## Q1 — Which hypothesis, and why (tied to the flags) **A. The `SendWhoFilters` table is what trips the restriction.** The 2-arg text form is callable from a genuine button press. The flag evidence only gets you partway: - `HasRestrictions = true` on **both** `SendWho` and `SendChatMessage` means "must run in a restricted-but-valid context" — the hardware-event rule. Torchcall's whispers already prove a button `OnClick` is such a context, so this flag is *not* the differentiator and cannot mean "addons may never call this." - `SecretArguments = "AllowedWhenUntainted"` on **both** governs *secret-typed* arguments accepted only when untainted. It does not literally mean "any addon-built table is forbidden" — that's an over-reading. What it does mean, practically, is that the one structural difference in the failing call matters: the third argument `{classIDs=…, raceIDs=…, uiMapIDs=…}` is a structured type produced only by Blizzard's secure GroupFinder path (`LFGWhoListFilterUtil.GetWhoFilters()`). An addon-constructed copy of it is tainted, so the client refuses the whole call. The 2-arg form (`text, origin`) is a plain string + enum — the exact shape `/who` and `FriendsFrame` send — and sits on the same footing as the whisper string, which the client accepts. So A is correct *operationally*: the overload, not the function, is the boundary. I'll state the nuance the critiques insisted on rather than overclaiming: `SecretArguments` doesn't by itself prove "table ⇒ blocked"; the block is best described as an overload-specific taint restriction. B is **disfavored, not falsified** — the flag parity with `SendChatMessage` makes B a poor explanation, but the 2-arg form hasn't yet been exercised live. That's exactly why the fix keeps a fallback that degrades to manual `/who` guidance if 2-arg is ever blocked too. The existing code already contains the fix's machinery: `whoFilters()` returns `nil` for `whoMode == "text"` (`Core.lua:511`), which drops into the 2-arg branch (`Core.lua:620`), and `StartSearch` already splits multi-class searches into one-per-class for text mode (`Core.lua:659-662`). ## Q2 — Does the 2-arg form return results reliably? SetWhoToUi gotcha Yes, but **`SetWhoToUi(true)` must stay.** This is where the council genuinely split, and Answer 1 got it wrong: - Answer 1 recommended switching to `SetWhoToUi(false)` ("addon-owned" pattern). **Wrong.** `SetWhoToUi` controls *routing*, not addon visibility: with `false`, small result sets (1–3) are delivered as `CHAT_MSG_SYSTEM` instead of firing `WHO_LIST_UPDATE`. Torchcall would read those as "no answer → 6s timeout" and look deader than before. `SetWhoToUi(false)` also does **not** reliably suppress the native window. - The current code is already right here: `setWhoToUi(true)` at `Core.lua:614`, then `setWhoToUi(false)` on receipt at `Core.lua:679`. Keep the `true`→restore lease. Other gotchas, all already handled or to keep handling: - **The native window does not "steal" the event.** `WHO_LIST_UPDATE` is broadcast to every registered frame; the FriendsFrame opening the WHO panel is cosmetic and independent. The reason no results ever land is that the blocked 3-arg send means `WHO_LIST_UPDATE` never fires at all — not that the window took them. - `GetNumWhoResults`/`GetWhoInfo` are plain getters (no `HasRestrictions`), readable regardless of the toggle; copy the fields immediately in the handler. - `WHO_LIST_UPDATE` carries no query id and the result buffer is global. The existing `pending` guard (`Core.lua:674`) + `onForeignWho` hook (`Core.lua:458-465`) already stop a manual `/who` or another addon from poisoning the list — keep them. - Multi-class text: one class per query (`c-"Mage"`). `queryText` already emits it (`Core.lua:523`), and the existing "server ignored the class part" fallback (`Core.lua:746-752`) still applies. ## Q3 — Self-heal (this is where the objection overrides Answer 1) The objection is **correct, and it is decisive**: the refusal is a **synchronous event**, not a late one, so a `pending`-gated detector never fires. Proof from this codebase, not the docs alone: - `sendChat` (`Core.lua:981-987`) does `chatRefused = false; pcall(send, …); if chatRefused then return false, NEEDS_PRESS end`. Reading the flag the instant `pcall` returns only works if `ADDON_ACTION_BLOCKED/FORBIDDEN` is dispatched **inside** the call. This is the addon's own working model of the event being synchronous. - The mock encodes exactly that: `tests/mock.lua:122` fires `ADDON_ACTION_FORBIDDEN` from *inside* `SendChatMessage`, before it returns, and `M.fire` (`mock.lua:226`) dispatches synchronously. - But `pending` is assigned **after** `SendWho` returns (`Core.lua:631`, after the `pcall` at `619-620`). So in `actionRefused`, `pending` is still `nil` when a synchronous who-block fires. Answer 1's `if pending then …` self-heal **never runs on the failure it's written for**. Worse, under Answer 1's snippet, the dropped `what:find("Who")` guard means a who-block (whose live payload is `"UNKNOWN()"` — no "Who" substring) inside the 3-second welcome window would fall through to the welcome-revert and *un-welcome a recruit*. The current test at `tests/run.lua:1524` stays green only because it fires a synthetic `"C_FriendList.SendWho()"` string the live client never produces. So: **do not key on `pending`, and do not key on a wall-clock window.** The event is synchronous, so the correlation signal is the call-active sentinel — and Torchcall already has one: - `sendingOurs` (`Core.lua:453`) is set `true` at `Core.lua:616` and cleared at `621`, around exactly one `SendWho` call. That is the who equivalent of `chatRefused`, and `onForeignWho` already uses it to tell our call from a foreign one. ### Concrete self-heal Module flag, mirroring `chatRefused`: ```lua local whoRefused = false ``` In `actionRefused` (`Core.lua:1313`), add the sentinel check **before** the string guard and the welcome-revert: ```lua local function actionRefused(addon, what) if addon ~= ADDON then return end ns.Log("refused", tostring(what)) chatRefused = true -- Our own who call is on the stack: the game refused that search. On this client the -- payload is "UNKNOWN()", so the string cannot name it — the call sentinel can. if sendingOurs then whoRefused = true return end -- a search or invite being stopped says nothing about the welcome before it (keep as-is) if type(what) == "string" and (what:find("Who", 1, true) or what:find("Invite", 1, true)) then return end -- ... existing welcome-revert untouched ... end ``` In `NextSearch` (`Core.lua:616-631`), reset the flag before the call and check it right after, *before* dequeuing: ```lua sendingOurs = true whoRefused = false local filters = whoFilters(q) local ok, err if filters then ok, err = pcall(C_FriendList.SendWho, queryText(q), origin, filters) else ok, err = pcall(C_FriendList.SendWho, queryText(q), origin) end sendingOurs = false if whoRefused then whoRefused = false setWhoToUi(false) if TorchcallDB.opts.whoMode ~= "text" then TorchcallDB.opts.whoMode = "text" -- persisted via SavedVariables -- plural .classes items can't be rendered as text: rebuild one-per-class -- (same loop as the existing "filter not honoured -> text" path, Core.lua:717-732) local plan = {} for _, item in ipairs(queue) do if item.classes then for _, token in ipairs(item.classes) do plan[#plan + 1] = { lo = item.lo, hi = item.hi, class = token, race = item.race, zone = item.zone } end else plan[#plan + 1] = item end end queue = plan ns.Log("who", "class-filter table refused by the client, asking in words from now on") end note("The game blocked that search's class filter, so Torchcall asks in words now. Press Continue.") return false -- do NOT dequeue, do NOT set pending, do NOT arm the timeout end if not ok then … end -- existing error path stays ``` Three things this gets right that Answer 1 got wrong: 1. **No `pending` gate.** The sentinel is `sendingOurs`, which is true during the call; the flag is read immediately after `pcall`, exactly like `chatRefused`. 2. **No re-send from the handler.** It flips a saved var, rebuilds the queue, and messages — the actual 2-arg send is the recruiter's next press. The press-driven invariant is untouched (the fuzz mock fires `ADDON_ACTION_FORBIDDEN` from timers precisely to catch any off-press send; this handler sends nothing). 3. **No welcome damage.** The early `return` on `sendingOurs` fires before the welcome-revert, so a synchronous who-block can never take a welcome mark back — and the existing `what:find("Who")` guard below it still handles any (hypothetical) late who-refusal with a readable payload, keeping `tests/run.lua:1524` green. A time window is *not* the primary signal and shouldn't be. `WHO_GAP=5`/`WHO_TIMEOUT=6` are far too broad to attribute a refusal reliably. The synchronous sentinel is exact; if you want belt-and-suspenders, a sub-second `GetTime() - lastWho` check is the most I'd add, but it's not needed once the sentinel is in place. ## Q4 — SetWhoToUi / taint pitfalls - `SetWhoToUi` has no `HasRestrictions`; literal `true`/`false` is untainted, callable from addon code. The taint is specifically the structured third argument — building the query **string** from SavedVariables/config is fine (strings aren't secret; that's the same mechanism that lets whisper text through). - Call `SetWhoToUi(true)` and `SendWho` only inside the OnClick path. Deferring either through `C_Timer.After` moves it off the hardware event and trips the invariant (the fuzz suite enforces this). No timer-driven send, no auto-advance. - **There is no public getter** for the current routing flag, so "restore to the native window's state" can only be approximated. The existing `setWhoToUi(false)` (`Core.lua:575-581`) already does the sensible thing: it reconstructs the native frame's `IsShown()` and applies that, rather than blindly forcing `false`. Leave it. `false` doesn't close an already-open native window anyway. - Don't try to "cleanse" the table with `securecallfunction`/`CopyTable`/`table.freeze` — that won't un-taint it and isn't needed once you stop passing it. --- ## Ranked recommended fix **1. Root fix — never build/pass the `SendWhoFilters` table on this client (Forever `camelot`/1.60.1).** Two prongs, both cheap: - Migration in `initDB` (near `Core.lua:152`): if the build is the camelot 1.60.1 family (capture `GetBuildInfo()` once at load, as already logged at `Core.lua:1857`), rewrite a saved/default `whoMode` of `"exclude"` or `"include"` to `"text"` (leave `"text"`/`"local"`). This fixes the already-saved `"exclude"` without asking the user to touch anything. - Belt-and-suspenders in `whoFilters()` (`Core.lua:509`): `return nil` on that client so the 3-arg branch can never be reached again. Optionally keep the 3-arg path behind a persisted capability flag for other clients. The per-class splitting, `c-"Mage"` encoding, and result filtering all already exist — no new query machinery. **2. Self-heal in `actionRefused`/`NextSearch`** exactly as in Q3: `sendingOurs`-gated `whoRefused` flag, flip `whoMode` to `"text"`, rebuild plural `classes` queue items to one-per-class, `setWhoToUi(false)`, log + one-line note, `return false` before dequeue/pending/timeout. No send from the handler. This is the backstop that keeps future clients or missed configs from silently going dead again. **3. Keep `SetWhoToUi(true)` through receipt; do not adopt Answer 1's `false`.** Copy `GetNumWhoResults`/`GetWhoInfo` immediately in the handler; restore best-effort via the existing `setWhoToUi(false)`. Distinguish three terminal states: blocked (Q3 path), `WHO_LIST_UPDATE` with zero rows ("0 online — nothing found"), and no response within `WHO_TIMEOUT` ("slow to answer / possibly throttled — press Continue"). **4. If the 2-arg form is ever also blocked synchronously** (the B contingency, not expected): persist a "manual" transport flag and show the exact native `/who` query for the user instead of attempting `SecureActionButton` tricks — there's no secure action type for arbitrary WHO, and the hardware event is already present. **5. Test gap to close:** the mock's `SendWho` (`tests/mock.lua:144`) models a block as a Lua `error("blocked")` (caught by the `pcall`), *not* as the live event — so the 750k-step suite cannot currently reproduce this regression. Add a mock path that fires `ADDON_ACTION_FORBIDDEN` synchronously from inside `SendWho` when filters `~= nil`, and assert: a blocked who produces zero `sentWho`/queue-advance, flips `whoMode` to `"text"`, does **not** un-welcome a recently-welcomed prospect, and sends nothing off-press; plus 1–3-result searches still deliver via `WHO_LIST_UPDATE`. --- ## Where the council genuinely disagreed - **`SetWhoToUi` direction**: Answer 1 said `false` (addon-owned), Answer 2 said `true`. The composite and the API routing semantics resolve it to **`true`** — `false` reroutes ≤3-result sets to `CHAT_MSG_SYSTEM` and would make small searches time out. (Critique 2's prose misattributed the two positions but its conclusion was right.) - **Self-heal correlation**: Answer 1 keyed on `pending`; Answer 2 and the objection keyed on a call-active sentinel. The objection wins — the event is synchronous and `pending` is set after the call.
